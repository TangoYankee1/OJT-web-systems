## 📜 PART 0: THE AI ASSISTANT'S PRIME DIRECTIVE

### 🔒 Non-Negotiable Rules

| # | Rule | Rationale |
| :--- | :--- | :--- |
| 1 | Never modify the database schema without explicit approval. | Schema changes break existing code. |
| 2 | Always use parameterized queries. | Prevent SQL injection. |
| 3 | Never store plaintext passwords. | Always use bcrypt/argon2 hashing. |
| 4 | Follow the exact table/column names from the Data Dictionary. | Consistency prevents runtime errors. |
| 5 | Every API endpoint must validate input before touching the DB. | Prevent bad data. |
| 6 | Every response must include proper HTTP status codes (200, 201, 400, 401, 403, 404, 500). | Standard REST practice. |
| 7 | Enforce role-based access on EVERY endpoint. | Security-first design. |
| 8 | Never expose the Supabase `service_role` key in frontend code. | Critical security breach. |
| 9 | Test every query in Supabase SQL Editor before writing backend code. | Verify logic works. |
| 10 | Log every error with sufficient context. | Debuggability. |
| 11 | If requirements are ambiguous, STOP and ask. | Never assume. |
| 12 | Every deliverable must be documented in Markdown. | Reproducibility. |

### 🎨 Coding Conventions

| Aspect | Convention |
| :--- | :--- |
| Database tables | `snake_case` (e.g., `placement_requirements`) |
| API endpoints | `kebab-case` (e.g., `/api/placement-requirements`) |

#### Task 1.5 — Create Views
```sql
CREATE OR REPLACE VIEW v_student_placements AS
SELECT 
    p.id AS placement_id,
    u.full_name AS student_name,
    s.student_number,
    s.course,
    s.year_level,
    uf.full_name AS faculty_supervisor,
    c.name AS company_name,
    cd.department_name AS company_department,
    p.start_date, p.end_date, p.status, p.deployment_type
FROM placements p
JOIN students s ON p.student_id = s.id
JOIN users u ON s.user_id = u.id
JOIN faculty f ON p.faculty_id = f.id
JOIN users uf ON f.user_id = uf.id
LEFT JOIN company_departments cd ON p.company_department_id = cd.id
LEFT JOIN companies c ON cd.company_id = c.id;

CREATE OR REPLACE VIEW v_placement_progress AS
SELECT 
    p.id AS placement_id,
    COUNT(DISTINCT pr.id) AS total_requirements,
    COUNT(DISTINCT pr.id) FILTER (WHERE pr.status = 'approved') AS approved_requirements,
    COALESCE(SUM(ws.total_hours), 0) AS total_hours_logged
FROM placements p
LEFT JOIN placement_requirements pr ON p.id = pr.placement_id
LEFT JOIN work_schedules ws ON p.id = ws.placement_id
GROUP BY p.id;
```

#### Task 1.6 — Trigger for verified_at
```sql
CREATE OR REPLACE FUNCTION update_verified_at()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.status IN ('approved', 'rejected') AND OLD.status != NEW.status THEN
        NEW.verified_at = NOW();
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_placement_requirements_verified
BEFORE UPDATE ON placement_requirements
FOR EACH ROW
EXECUTE FUNCTION update_verified_at();
```

#### Task 5.2 — Auto-populate Requirements
```javascript
async function createPlacement(data) {
    const { data: placement } = await supabase
        .from('placements').insert(data).select().single();

    const { data: requirements } = await supabase
        .from('requirements').select('id').eq('is_required', true);

    const prRows = requirements.map(r => ({
        placement_id: placement.id,
        requirement_id: r.id,
        status: 'pending'
    }));

    await supabase.from('placement_requirements').insert(prRows);
    return placement;
}
```

#### Task 7.3 — Score Computation
```sql
SELECT 
    e.id,
    SUM(es.score) AS total,
    SUM(ec.max_score) AS max,
    ROUND((SUM(es.score)::DECIMAL / SUM(ec.max_score)) * 100, 2) AS percentage
FROM evaluations e
JOIN evaluation_scores es ON e.id = es.evaluation_id
JOIN evaluation_criteria ec ON es.criterion_id = ec.id
WHERE e.id = ?
GROUP BY e.id;
```
